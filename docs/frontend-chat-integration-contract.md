# Frontend Chat Integration Contract

This document defines the integration boundary to preserve when replacing the Power Apps chat UI with a custom frontend. The Foundry agent and Azure Function behavior remain unchanged.

The corresponding Azure Function implementation is stored for reference in [`manufacturing-chat-api-reference.js`](./manufacturing-chat-api-reference.js).

## Request flow

```text
Power Apps or custom frontend
        |
        | POST /api/chat
        v
Azure Function: manufacturing chat API
        |
        | Managed Identity access token
        v
Microsoft Foundry Agent endpoint
        |
        v
Azure Function JSON response
        |
        v
Power Apps or custom frontend
```

The frontend does not call Foundry directly. The Azure Function owns Foundry authentication, request translation, response parsing, and the Power Apps-specific HTML conversion.

## Frontend to Azure Function

### Endpoint

```http
POST https://<function-app-domain>/api/chat
Content-Type: application/json
```

### Request body

```json
{
  "message": "How many tables do you have access to?",
  "previous_response_id": "",
  "agent_session_id": ""
}
```

| Field | Required | Meaning |
|---|---:|---|
| `message` | Yes | Current user message. Blank or whitespace-only values return HTTP 400. |
| `previous_response_id` | No | Foundry response ID from the immediately preceding turn. Empty on the first turn. |
| `agent_session_id` | No | Foundry agent session ID when one is returned. Empty when unused. |

The frontend must keep the two identifiers in memory for the current chat. Starting a new chat clears both values.

### Successful response

```json
{
  "answer": "The dataset contains **17 business tables**...",
  "answer_html": "<div style='...'>The dataset contains <strong>17 business tables</strong>...</div>",
  "response_id": "resp_abc123",
  "agent_session_id": ""
}
```

| Field | Meaning |
|---|---|
| `answer` | Raw assistant answer in Markdown. The custom frontend should render this field. |
| `answer_html` | Power Apps-oriented HTML generated by `markdown-it` with inline styles. Retained for compatibility with the existing app. |
| `response_id` | Current Foundry response ID. Send it as `previous_response_id` on the next turn. |
| `agent_session_id` | Current Foundry agent session ID, if supplied. Send it on the next turn. |

### Error response

The Function returns HTTP 500 with this shape:

```json
{
  "error": "actual backend error message",
  "answer": "I couldn't complete that analysis. Please try again.",
  "answer_html": "<p>I couldn't complete that analysis. Please try again.</p>",
  "response_id": "",
  "agent_session_id": ""
}
```

The frontend should show the safe `answer` text or its own equivalent retry message. It should not display `error` to the user.

## Multi-turn state

```text
Turn 1 request:  previous_response_id = ""
Turn 1 response: response_id = "resp_123"

Turn 2 request:  previous_response_id = "resp_123"
Turn 2 response: response_id = "resp_456"

Turn 3 request:  previous_response_id = "resp_456"
```

Only the most recent `response_id` and `agent_session_id` need to be retained. This application does not require database persistence; refreshing the page or starting a new chat may reset the conversation.

## Azure Function to Foundry

The Function reads the Foundry URL from `FOUNDRY_AGENT_ENDPOINT`, adds `api-version=v1`, and requests an Entra access token for `https://ai.azure.com` using the Function App managed identity.

It sends:

```http
POST <FOUNDRY_AGENT_ENDPOINT>?api-version=v1
Authorization: Bearer <managed-identity-token>
Content-Type: application/json
```

First turn:

```json
{
  "input": [
    {
      "role": "user",
      "content": "How many tables do you have access to?"
    }
  ],
  "stream": false
}
```

Later turns add the identifiers when present:

```json
{
  "input": [
    {
      "role": "user",
      "content": "Which ones contain late-order risk?"
    }
  ],
  "stream": false,
  "previous_response_id": "resp_123",
  "agent_session_id": ""
}
```

The Function extracts assistant text from `output_text` when available. Otherwise, it joins `output_text` content items from message entries in `output[]`.

## Existing Power Apps behavior

Power Apps calls the Function through the `ManufacturingAgentPOC.Chat(...)` custom connector. On success it:

1. Adds `answer` and `answer_html` to the visible chat collection.
2. stores `response_id` as `varPreviousResponseId`.
3. stores `agent_session_id` as `varAgentSessionId`.
4. sends those values with the next message.

The custom frontend must preserve the same state transition even though it does not need the Power Apps-specific collection or HTML rendering.

## Reported deployed configuration

These settings describe the currently deployed integration but are not independently represented by files in this repository:

- The HTTP-triggered Function route is `api/chat`.
- The deployed `function.json` uses `authLevel: "anonymous"`.
- The Power Apps custom connector is configured with API Key authentication.
- The current Foundry call is non-streaming.

If the deployed Function configuration changes, update this section and the frontend environment settings. Preserve the JSON request and response shapes unless both clients are updated together.
